## 2. Изменения порядка относительно мастер-промпта

Мастер-промпт предлагал: модули (8) → голос (9) → уведомления (10) → бэкап (11) → тестирование (12). План изменён:

| Изменение | Почему |
|---|---|
| **Уведомления — внутри вехи M2**, вместе с задачами | Задача без напоминания неполноценна; согласование базы и ОС (ARCHITECTURE §13) проще строить сразу, чем встраивать потом |
| **Бэкап и безопасность — веха M3**, сразу после задач и финансов | Пользоваться приложением «по-настоящему» без бэкапа нельзя: данные хранятся только на телефоне. Шифрование базы включается ещё раньше — в инфраструктуре (этап 7) |
| **Тестирование — непрерывно**, плюс отдельный этап стабилизации перед выпуском | Тесты пишутся вместе с кодом (TESTING_STRATEGY §1); этап 12 — только общий прогон, исправления и проверки на устройствах |
| **Технические пробы — первым делом этапа 7** | Шесть гипотез (ARCHITECTURE §22) могут изменить решения; их нужно проверить до того, как на них построено приложение |

## 3. Этапы 7–14

Оценки — **относительные** (S ≈ 1 неделя, M ≈ 2–3, L ≈ 4–6) при допущении ~15 часов работы в неделю с помощью ИИ-инструментов [Гипотеза]. Это ориентир для планирования, а не обещание. Фактическое время записывается после каждой вехи, и план уточняется.

### Этап 7. Базовая инфраструктура и технические пробы — M
- **Цель:** рабочий «скелет» приложения на обеих платформах, на котором можно строить функции, и подтверждённые технические гипотезы.
- **Входные данные:** ARCHITECTURE, DATABASE (структура), DESIGN_SYSTEM (токены), DATA_SECURITY §3.
- **Шаги:**
  1. **Пробы P1–P6** (ARCHITECTURE §22), каждая — отдельная маленькая ветка с выводом в DECISIONS.md:
     - P1 — workspace;
     - P2 — sqlite3mc на Android и iOS;
     - P3 — FTS5;
     - P4 — уведомления;
     - P5 — распознавание русского;
     - P6 — Argon2id.
     Отдельно — `VACUUM INTO` и перешифровка снимка, работа без разрешения `INTERNET`.
  2. Репозиторий Git, ветки, шаблон PR, `README.md`, **`CLAUDE.md`** (правила проекта для ИИ-инструментов, §5).
  3. Workspace `core` + `app`, окружения dev / prod, иконка-заглушка.
  4. CI: GitHub Actions (TESTING_STRATEGY §8) и Codemagic (iOS без подписи); первая установка на iPhone через Sideloadly.
  5. Дизайн-система в коде: токены светлой и тёмной темы, шкала шрифтов, базовые компоненты (строка списка, заголовок раздела, нижняя панель, сегментированный переключатель, кнопки, форма).
  6. Навигация: оболочка с 5 вкладками, пустые экраны-заглушки, охранник маршрутов.
  7. База: подключение с шифрованием, ключ в защищённом хранилище, `beforeOpen` (FK, WAL), механизм миграций, снимок схемы v1, генератор тестовых данных.
  8. Общие сервисы: `Clock`, `Result` / `AppFailure`, логгер с ротацией, глобальный перехват ошибок, локализация (ARB, ru), `UnitOfWork`.
- **Результаты:** приложение запускается на эмуляторе Android и iPhone: пустые вкладки в обеих темах, зашифрованная база создаётся и открывается, CI зелёный.
- **Зависимости:** этап 6 согласован.
- **Критерии завершения:**
  - все пробы выполнены, их результаты записаны; решения при необходимости пересмотрены и согласованы;
  - CI проверяет форматирование, анализ, тесты, импорты, манифест;
  - сборка iOS из Codemagic установлена на iPhone.
- **Риски:**
  - отрицательный результат пробы (особенно P2, P3, P5) → пересмотр решения до начала M1;
  - сложности подписи и установки на iPhone через Sideloadly.
- **Тесты:** unit для `Money` (первые), логгер (AC-24), контраст токенов, smoke-тест открытия базы, тест миграции «пустая база → v1».
- **Документация:** README, CLAUDE.md, DECISIONS (пробы), обновления ARCHITECTURE при отклонениях.

### Этап 8. Основные модули — вехи M1–M5 (L × 4)

#### M1 Финансы: ядро — L
- **Цель:** вести учёт денег каждый день.
- **Содержание:**
  - онбординг (SCR-02);
  - счета (SCR-34/35);
  - категории со стандартным набором (SCR-42/43);
  - валюты и курсы (SCR-44);
  - расход, доход, перевод (SH-01…03);
  - операции и операция (SCR-31/32);
  - обзор денег (SCR-30) без бюджетов и долгов;
  - глобальный поиск (SCR-70) по операциям.
- **Критерии завершения:**
  - AC-01, 02, 03, 16, 17 зелёные;
  - S1 ≤ 3 нажатий подтверждено интеграционным тестом;
  - NFR-PERF-03 на 10 000 операций;
  - чек-лист устройства (частично: темы, шрифт, диктор на S1).
- **Риски:** ошибки в денежной модели — самые дорогие; поэтому сначала `core/money` и `core/finance` с тестами по REQUIREMENTS §6.
- **Порядок работы (шаги вехи, каждый проверяется отдельно):**
  1. `core/finance`: модели, правила `report_effect`, баланс, общий баланс, итоги периода, курсы; тесты AC-01, 02, 03, 16, 17 на уровне ядра.
  2. Данные: таблицы `account`, `category`, `exchange_rate`, `fin_transaction` с ограничениями и триггерами, репозитории, сценарии; тесты на базе в памяти.
  3. Экраны: онбординг, быстрый ввод расхода, дохода и перевода, обзор денег, счета, операции.
  4. Экраны: категории, валюты и курсы, поиск; замер на 10 000 операций; чек-лист.

#### M2 Продуктивность — L
- **Содержание:**
  - задачи, подзадачи, серии повторов (SCR-20/21/28, SH-04);
  - проекты и цели (SCR-22…25);
  - **напоминания** (ReminderScheduler, разрешения, SCR-85);
  - экран «Сегодня» (SCR-10) без привычек и календаря;
  - журнал действий в фоне (запись, без экрана).
- **Критерии завершения:**
  - AC-07…10 зелёные;
  - уведомления приходят на iPhone и эмуляторе (ручной чек-лист);
  - S4 ≤ 5 нажатий;
  - тест «5 секунд» на «Сегодня».
- **Риски:** точные будильники и энергосбережение Android (проверяются только на эмуляторе, D-009).

#### M3 Бэкап и безопасность — M
- **Содержание:**
  - автокопии и экспорт `.uabk`, восстановление (SCR-88/89/90), строка состояния бэкапа;
  - PIN и биометрия, автоблокировка, скрытие содержимого (SCR-01, SCR-91);
  - корзина и «Отменить» (SCR-73);
  - удаление всех данных (SCR-93);
  - восстановление после сбоя (SCR-03).
- **Критерии завершения:**
  - AC-11…14, 25 и TX-ATOMIC зелёные;
  - перенос iPhone ↔ эмулятор выполнен вручную;
  - чек-лист безопасности DATA_SECURITY §13.
- **После M3** приложением можно пользоваться в реальной жизни. Владелец начинает собирать собственные фразы для голосового корпуса и замечания по удобству.

#### M4 Планирование денег — M
- **Содержание:**
  - регулярные платежи и плановые операции (SCR-38/39, SCR-13);
  - бюджеты (SCR-36/37);
  - долги (SCR-40/41);
  - накопительные цели;
  - шаблоны (SCR-45);
  - аналитика (SCR-33) с переходом к операциям;
  - «Можно потратить» на «Сегодня» и в обзоре.
- **Критерии завершения:** AC-18, 19, 20 зелёные; NFR-PERF-04 (аналитика на 50 000 операций); двойной счёт агрегатов (TESTING_STRATEGY §3.1).

#### M5 Заметки, календарь, история — M
- **Содержание:**
  - заметки (SCR-50…52), теги (SCR-71/72), связи (SCR-74);
  - календарь и «Предстоящие» (SCR-11/12) с системным календарём только для чтения;
  - журнал действий (SCR-14), история изменений на экранах записей;
  - поиск по всем типам.
- **Критерии завершения:** AC-22 зелёный; поиск ≤ 300 мс (NFR-PERF-05); FR-NOT-05 (автосохранение после принудительного закрытия).

### Этап 9. Голосовой ввод — веха M6 — L
- **Цель:** надиктовать несколько записей разных типов и сохранить после проверки.
- **Входные данные:** VOICE_INPUT; корпус фраз владельца, собранный после M3.
- **Содержание:**
  - конвейер `core/voice` по этапам (сначала тесты по корпусу);
  - `SystemSpeechRecognizer`;
  - экраны SCR-60…63;
  - сохранение через сценарии модулей;
  - пользовательские синонимы (SCR-87).
- **Зависимости:** M1, M2, M5 (все типы записей, которые создаёт голос, существуют и стабильны).
- **Критерии завершения:**
  - корпус ≥ 150 фраз, совпадение ≥ 80%, **0 выдуманных полей**;
  - AC-04, 05, 06, 26 зелёные;
  - ручная проверка на iPhone (on-device) и эмуляторе.
- **Риски:** качество правил на живой речи (смягчение — корпус собственных фраз); недоступность распознавания на части Android-устройств (ввод текстом есть всегда).
- **Документация:** VOICE_INPUT (уточнённые правила и веса), отчёт по метрике корпуса.

### Этап 10. Привычки, импорт CSV, доработки — веха M7 — M
- **Содержание:**

## 4. Правило перехода между этапами и вехами
Мастер-промпт §18: не переходить без проверки результата. Перед каждым переходом:
1. Критерии завершения выполнены и проверены (команды и результаты в отчёте).
2. Чек-лист устройства для этой вехи пройден, результат записан в `docs/test-runs/M<n>.md`.
3. Документация обновлена: отклонения → DECISIONS.md; изменённое поведение → REQUIREMENTS / UI_SPECIFICATION.
4. Краткий обзор с владельцем: что сделано, что отложено, сколько заняло времени, нужна ли корректировка плана.

## 5. Работа с ИИ-инструментами (мастер-промпт §20)

### 5.1 `CLAUDE.md` (создаётся на этапе 7)
Файл в корне репозитория, который Claude Code и подобные инструменты читают автоматически. Содержание:
- краткое описание продукта и ссылки на документы (что читать для какой задачи);
- архитектурные правила (ARCHITECTURE §1.3), денежные правила (никаких `double`, только `Money`);
- список «Чего не делать» из DESIGN_SYSTEM §15;
- команды: запуск, тесты, анализ, генерация drift;
- 20 правил мастер-промпта §20 в сжатом виде;
- Definition of Done (TESTING_STRATEGY §10).

### 5.2 Размер задачи
Одна задача для ИИ — **одна проверяемая единица**: «модель `Money` и её тесты», «таблица `account` + DAO + репозиторий + тесты», «экран SCR-34 по UI_SPECIFICATION». Не «сделай финансы».

Пример разбиения M1 на задачи (каждая — отдельная ветка и PR):
1. `core/money`: `Currency` (таблица ISO 4217), `Money`, округление, форматирование + тесты.
2. `core/finance`: баланс, доходы и расходы, `report_effect` + тесты по REQUIREMENTS §6.
3. Таблицы `account`, `category`, `exchange_rate`, `fin_transaction` + миграция v1 + DAO + тесты инвариантов I1–I4, I8, I13.
4. Репозитории и сценарии: добавить расход / доход, перевод, корректировка + тесты AC-01…03.
5. Стандартные категории (сид) + «Восстановить стандартные».
6. Онбординг SCR-02.
7. Компонент клавиатуры суммы + SH-02.
8. SH-03 перевод.
9. SCR-31 / SCR-32 операции + фильтры.
10. SCR-34 / SCR-35 счета, корректировка баланса.
11. SCR-44 курсы, пометка «неполный итог».

### 5.3 Шаблон запроса к ИИ-инструменту
```
Задача: <одна единица из списка вехи>.

Сделай: <что именно, какие файлы>.
```

### 5.4 Правила проверки работы ИИ
- Запускать указанные команды самостоятельно и смотреть результат.
- Не принимать «протестировано» без вывода тестов.
- Если ИИ предлагает изменить архитектуру или добавить библиотеку — сначала обсуждение и запись в DECISIONS.md.
- Если найдено противоречие между документами — остановиться и решить его до реализации (§20, правило 17).
