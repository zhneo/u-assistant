## 1. Архитектурный подход

### 1.1 Решение: модульный монолит с тремя слоями и отдельным «ядром» на чистом Dart

```
┌────────────────────────────────────────────────────────────┐
│  app  (Flutter)                                            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ Представление: экраны, компоненты дизайн-системы,     │  │
│  │ контроллеры состояния (Riverpod)                      │  │
│  └───────────────┬──────────────────────────────────────┘  │
│                  │ вызывает                                │
│  ┌───────────────▼──────────────────────────────────────┐  │
│  │ Приложение: сценарии (use cases) — «сохранить        │  │
│  │ расход», «выполнить задачу», «восстановить бэкап»     │  │
│  └──────┬─────────────────────────────┬─────────────────┘  │
│         │ использует интерфейсы       │                    │
│  ┌──────▼──────────────┐   ┌──────────▼─────────────────┐  │
│  │ Данные: drift, DAO, │   │ Платформа: уведомления,    │  │
│  │ репозитории         │   │ речь, файлы, Keychain,     │  │
│  │                     │   │ биометрия, календарь       │  │
│  └─────────────────────┘   └────────────────────────────┘  │
└──────────────────────────┬─────────────────────────────────┘
                           │ зависит от
┌──────────────────────────▼─────────────────────────────────┐
│  core  (чистый Dart, без Flutter)                          │
│  Доменные модели и правила: деньги, финансовые расчёты,    │
│  повторения, разбор голоса, формат бэкапа, валидация       │
└────────────────────────────────────────────────────────────┘
```

> **Простыми словами.** Приложение делится на этажи. Нижний этаж, `core`, знает правила: как считать бюджет, когда следующий повтор задачи, как разобрать фразу. Он ничего не знает о экранах, базе и телефоне, поэтому его легко проверять тестами прямо на Windows. Верхние этажи используют эти правила. Экраны не лезут в базу напрямую: они просят сценарий («сохрани расход»), а сценарий сам решает, что записать и какие уведомления пересчитать.

**Почему так:**
- **Тестируемость на Windows без устройства.** iOS доступен только через облако (D-003), поэтому чем больше логики проверяется обычными unit-тестами, тем лучше (NFR-MNT-01).
- **Правила не размазаны по экранам.** Финансовая формула живёт в одном месте, и экран её не повторяет.
- **Будущая синхронизация** (D-005) подключается на уровне данных и не трогает экраны.

**Альтернативы:**

| Вариант | Почему не выбран |
|---|---|
| «Всё в виджетах» (логика в `StatefulWidget`) | Быстро в начале, но финансы и повторения станут нетестируемыми; прямо запрещено мастер-промптом |
| Полная Clean Architecture (сущности → use cases → интерфейсы → реализации → DTO → мапперы на каждый слой) | Десятки файлов на одну фичу; для одного разработчика-ученика избыточно. Мы берём идею (зависимости направлены внутрь), но без лишних слоёв |
| BLoC-архитектура | Работает, но больше шаблонного кода; Riverpod выбран в TECH_RESEARCH §8 |

**Цена:** немного больше файлов, чем «всё в виджетах»; нужна дисциплина в импортах (проверяется линтером, §1.3).

### 1.2 Организация кода: Dart workspace из двух пакетов

```
u-assistant/
├── pubspec.yaml               # корень workspace (Dart ≥ 3.6 — [Факт])
├── packages/
│   └── core/                  # чистый Dart: нет зависимости от Flutter
│       ├── lib/src/
│       │   ├── money/         # Money, Currency (ISO 4217), округление, курсы
│       │   ├── finance/       # баланс, бюджеты, долги, «можно потратить»
│       │   ├── recurrence/    # правила повторения, следующий экземпляр
│       │   ├── tasks/         # статусы, приоритеты, правила переноса
│       │   ├── voice/         # конвейер разбора: нормализация → черновики
│       │   ├── backup/        # формат файла, манифест, версии
│       │   └── common/        # Result, ошибки, идентификаторы, время
│       └── test/
└── app/                       # Flutter-приложение
    ├── lib/
    │   ├── main.dart
    │   ├── bootstrap/         # запуск: блокировка → база → миграции → тема
    │   ├── design_system/     # токены, тема, компоненты DESIGN_SYSTEM §8
    │   ├── features/
    │   │   ├── today/         # SCR-10..14
    │   │   ├── tasks/         # задачи, проекты, цели, привычки
    │   │   ├── money/         # счета, операции, аналитика, бюджеты, долги
    │   │   ├── notes/
    │   │   ├── voice/
    │   │   ├── quick_add/
    │   │   ├── search/
    │   │   ├── settings/      # включая бэкап и безопасность
    │   │   └── onboarding/
    │   ├── data/              # drift: таблицы, DAO, миграции, репозитории
    │   ├── platform/          # адаптеры ОС за интерфейсами
    │   ├── services/          # сценарии, общие для фич: напоминания, бэкап
    │   └── routing/           # go_router
    ├── test/                  # widget- и интеграционные тесты
    ├── integration_test/      # сценарии на устройстве или эмуляторе
    ├── ios/  android/
    └── l10n/                  # строки интерфейса (ARB), ru
```

Внутри каждой фичи — одинаковая раскладка:
```
features/money/
├── application/   # сценарии фичи: add_expense.dart, transfer.dart
├── presentation/  # экраны и контроллеры: operations_screen.dart, operations_controller.dart
└── widgets/       # компоненты, специфичные для фичи
```

**Почему workspace из двух пакетов, а не один:** граница «ядро без Flutter» проверяется компилятором. Если в `core` случайно импортировать Flutter, сборка упадёт. В одном пакете это держалось бы только на внимательности. [Гипотеза] Flutter-приложение в одном workspace с чистым Dart-пакетом работает без особенностей; это проверяется первым шагом этапа 7.

**Почему фичи, а не слои по всему приложению** (`screens/`, `models/`, `services/` на верхнем уровне): всё про деньги лежит рядом, проще найти и проще дать ИИ-инструменту узкую задачу «только в `features/money`».

### 1.3 Правила зависимостей (проверяются)
1. `core` не импортирует ничего из `app` и из Flutter.
2. `presentation` не импортирует `data` и `platform` напрямую — только через провайдеры сценариев и репозиториев.
3. Фича не импортирует внутренности другой фичи. Общее выносится в `services/` или `core`.
4. `platform` — только адаптеры: реализации интерфейсов, объявленных в `services` или `core`.

Проверка: правила `analysis_options.yaml`, ревью и тест-скрипт в CI, который ищет запрещённые импорты (`grep` по путям) [П].

## 3. Состояние приложения

**Решение:** Riverpod 3 **без** кодогенерации провайдеров [П].

- **Данные из базы** — `StreamProvider`, подписанный на запрос drift (`watch()`). Экран обновляется сам после любого изменения.
- **Состояние экрана** (выбранный фильтр, введённая сумма) — `Notifier` / `AsyncNotifier` в `presentation` фичи.
- **Сценарии и репозитории** — обычные `Provider`. В тестах подменяются через `ProviderScope(overrides: …)`.
- Бизнес-логика живёт в сценариях и `core`, **не в провайдерах**. Провайдер только соединяет (TECH_RESEARCH §8, риск смены API).

**Почему без `riverpod_generator`:** меньше «магии» для изучающего разработчика. Генератор кода уже нужен для drift, второй слой генерации усложнит понимание ошибок. Если позже шаблонного кода станет слишком много, генератор можно включить постепенно.

> **Простыми словами.** Провайдер — это «розетка», из которой экран получает данные или функцию. Экран говорит «дай мне список операций за октябрь» и автоматически перерисовывается, когда список меняется. Откуда список берётся — экрану неважно, поэтому в тестах вместо настоящей базы можно подключить тестовую.

## 4. Навигация

**Решение:** `go_router` с `StatefulShellRoute.indexedStack` для нижней панели.

- **5 веток:** Сегодня, Дела, Добавить (не ветка, а действие — открывает SH-01), Деньги, Заметки. Каждая ветка хранит свой стек (UI_SPECIFICATION §0.4).
- **Адреса экранов** — читаемые пути: `/today`, `/tasks/task/:id`, `/money/operations?category=…&from=…`. Через адрес открываются уведомления (deep link), а фильтр аналитики → операций передаётся параметрами.
- **Листы** (SH-01…04, выборы) — не маршруты, а `showModalBottomSheet` / Cupertino sheet из контроллера. Исключение — полноэкранные формы, у которых должен работать «Назад».
- **Охранник маршрутов:** пока приложение заблокировано (SCR-01) или не пройден онбординг (SCR-02), любой адрес ведёт туда. Ссылка из уведомления запоминается и открывается после разблокировки.

**Альтернатива:** встроенный `Navigator 2.0` вручную — гибко, но много кода. `auto_route` — сторонний генератор. `go_router` официальный и в режиме «feature-complete», то есть API стабилен [Факт, TECH_RESEARCH §8].

## 5. Слой доступа к данным

**Решение:** drift поверх sqlite3 3.x с шифрованием SQLite3MultipleCiphers (TECH_RESEARCH §2). Шифр по умолчанию — ChaCha20-Poly1305 [Факт].

```
Экран → Контроллер → Сценарий → Репозиторий → DAO (drift) → SQLite (зашифрованная)
```

- **Таблицы drift** описываются на Dart, генератор (`build_runner`) создаёт типизированные классы.
- **DAO** — один на модуль. Содержит запросы, включая агрегаты для аналитики, написанные на SQL в `.drift`-файлах с проверкой при генерации.
- **Репозиторий** — интерфейс в `services`/`core` и реализация в `data`. Переводит строки базы в доменные модели `core` и обратно. Экран никогда не видит классы drift.
- **Транзакции** открывает сценарий, а не репозиторий: «сохранить голосовые черновики» трогает три модуля в одной транзакции (NFR-REL-01). Для этого есть `UnitOfWork.run(() async { … })` — обёртка над `db.transaction`.
- **Фоновый поток:** база открывается через `NativeDatabase.createInBackground`, поэтому тяжёлые запросы не тормозят интерфейс.

> **Простыми словами.** DAO знает, как сделать запрос к таблице. Репозиторий знает, что такое «операция» в смысле приложения, и прячет детали таблиц. Сценарий знает порядок действий: проверить, записать, пересчитать напоминания, добавить запись в журнал.

## 7. Модели

- **Доменные модели** — неизменяемые классы в `core` (`final` поля, `copyWith`, равенство по значению). Для краткости кода рассматривается пакет `freezed` [П, проверить лицензию и актуальность на этапе 7]. Альтернатива — писать вручную (меньше зависимостей).
- **Значимые типы** вместо «голых» строк и чисел:
  - `Money(amountMinor: int, currency: Currency)` — арифметика только между одинаковыми валютами;
  - `CurrencyCode` — проверенный ISO-код;
  - `LocalDate` — дата без времени;
  - `EntityId` — UUID v7;
  - `ExchangeRate(value: Decimal)`;
  - `Percent`.
- **Перечисления** для статусов и типов (`TaskStatus`, `TransactionKind`). В базе — тот же набор значений и `CHECK` (DATABASE.md).

> **Простыми словами.** `Money` не даст случайно сложить тенге с долларами или записать сумму с плавающей точкой: такой код просто не скомпилируется. Это дешёвая страховка от самых опасных финансовых ошибок.

**Идентификаторы — UUID v7** [Факт: пакет `uuid` 4.6.0, MIT, поддерживает v7]. Создаются на устройстве, упорядочены по времени (удобно для индексов) и уникальны глобально — это нужно для переноса и будущей синхронизации (NFR-REL-07).

## 9. Обработка ошибок

**Решение:** ожидаемые ошибки — значения, неожиданные — исключения, которые ловятся на границе.

- **В `core` и сценариях** ожидаемые ошибки возвращаются как `Result<T, AppFailure>`. `AppFailure` — закрытый (`sealed`) набор вариантов:
  - `ValidationFailure(field, reason)` — сумма 0, пустое название;
  - `NotFound`;
  - `ConflictFailure` — счёт с операциями нельзя удалить без переноса;
  - `MissingRate(currency)`;
  - `StorageFailure` — нет места, ошибка записи;
  - `PermissionDenied(kind)`;
  - `BackupFailure(kind)` — повреждён, новее, неверный пароль;
  - `RecognitionUnavailable`.
- **Неожиданные исключения** (баг, падение плагина) ловятся в контроллере и глобально (`FlutterError.onError`, `PlatformDispatcher.instance.onError`). Пишутся в технический журнал **без пользовательских данных**. Пользователь видит «Что-то пошло не так. Данные не изменены» и кнопку «Повторить».
- **Каждый `AppFailure` переводится в текст** по правилу USER_FLOWS P8 (что случилось → сохранились ли данные → что делать) в одном месте: `failure_messages.dart`.
- **Транзакции** откатываются автоматически при любом исключении внутри `UnitOfWork.run`.

> **Простыми словами.** Если пользователь ввёл ноль — это не авария, а обычная ситуация, и код обрабатывает её как значение «ошибка проверки, поле сумма». Если же сломался плагин — это авария; её ловят, записывают в журнал и показывают спокойное сообщение. Так приложение не падает и не теряет данные.

## 10. Логирование

- **Собственный лёгкий логгер** поверх `package:logging` (официальный пакет Dart) [П].
- **Уровни:** `debug` (только в отладочной сборке), `info`, `warning`, `error`.
- **Запись** — в ротируемый файл в песочнице приложения: ≤ 1 МБ × 2 файла или 30 дней (FR-HIS-04). Экспорт — только по действию пользователя (SCR-94).
- **Запрещено логировать:** тексты задач и заметок, названия, суммы, распознанную речь, имена контрагентов, пути с личными именами. В лог пишутся типы событий и идентификаторы: «`transaction.save failed: StorageFailure(diskFull) id=0191…`».
- **Проверка:** unit-тест логгера с «запрещёнными» данными и ручная проверка AC-24.
- **Отправки отчётов о сбоях во внешние сервисы нет** (FR-SEC-07).

## 11. Миграции базы данных

- drift: `schemaVersion` + `MigrationStrategy.onUpgrade` со **ступенчатыми миграциями** (`stepByStep`), сгенерированными из сохранённых снимков схемы (`drift_dev schema dump` → папка `drift_schemas/` в репозитории).
- **На каждую версию — тест** «база старой версии с данными → новая версия, данные на месте», который генерирует `drift_dev`. Тесты запускаются на Windows в CI (NFR-REL-03).
- **Перед миграцией — автокопия** (NFR-REL-04). Миграция выполняется в транзакции. При ошибке база остаётся старой версии, пользователь видит SCR-03 с предложением восстановления.
- **Правила изменения схемы:**
  - только добавлять;
  - переименование и удаление — через новую колонку + перенос данных + удаление в следующей версии;
  - значения по умолчанию у новых обязательных колонок обязательны.
- **Бэкап хранит версию схемы.** Восстановление из старой версии прогоняет миграции на копии до подмены (BACKUP_AND_RESTORE.md).
- `PRAGMA foreign_keys = ON` и `PRAGMA journal_mode = WAL` включаются в `beforeOpen` [Факт*: в SQLite внешние ключи по умолчанию выключены].

## 12. Фоновые операции

| Операция | iOS | Android | Гарантия |
|---|---|---|---|
| Автобэкап | При уходе в фон (не чаще раза в N часов); `BGProcessingTask` — бонус | При уходе в фон; WorkManager раз в сутки (`requiresStorageNotLow`) | Время не гарантируется; статус виден пользователю (FR-BAK-09, 13) |
| Согласование уведомлений | При запуске и возврате в приложение; `BGAppRefreshTask` — бонус | При запуске, возврате, после перезагрузки (boot receiver плагина), WorkManager раз в сутки | Окно уведомлений рассчитано с запасом (§13) |

Пакет — `workmanager` (обёртка над WorkManager и BGTaskScheduler) [Факт, TECH_RESEARCH §5].

> **Простыми словами.** Телефон сам решает, когда дать приложению поработать в фоне, и может не дать вовсе. Поэтому всё важное делается и при открытии приложения, а фоновые задачи — приятный бонус. Пользователь всегда видит, когда была последняя копия.

## 13. Система уведомлений

**Принцип:** база — источник истины. Уведомления ОС — производная, которую можно в любой момент пересоздать (FR-REM-02).

```
┌──────────────┐  изменение    ┌────────────────────┐ желаемый набор ┌────────────────────┐
│ Сценарий     │──────────────▶│ ReminderScheduler  │───────────────▶│ diff с тем, что    │
│ (сохранить   │  (после       │ desiredOccurrences │                │ запланировано      │
│  задачу)     │   commit)     │ (окно)             │                │ (таблица + ОС)     │
└──────────────┘               └────────────────────┘                └─────────┬──────────┘
                                                                     отменить / запланировать
                                                                               ▼
                                                                  flutter_local_notifications
```

1. **Таблица `reminder`** хранит правила: абсолютное время, «за N минут до», ежедневное время (привычки).
2. **Окно:** вычисляются ближайшие срабатывания — на iOS не больше 50 (лимит ОС 64 [Факт]), на Android — на 14 дней вперёд.
3. **Таблица `scheduled_notification`** хранит, что именно запланировано в ОС: ID уведомления, ID напоминания, время. ID уведомления — стабильное 31-битное число, выведенное из ID напоминания и номера срабатывания.
4. **Согласование** (`reconcile`) — идемпотентное: одинаковый результат при любом числе вызовов. Отменяет лишнее, планирует недостающее.
5. **Порядок:** сначала коммит в базу, потом `reconcile`. Если приложение упадёт между ними, следующий запуск всё исправит. Поэтому «удалённая задача не оставляет активного напоминания» (AC-07) гарантируется самое позднее к следующему открытию, а обычно — сразу.
6. **Точные будильники на Android:** проверка `canScheduleExactAlarms()`. Если нельзя — неточный режим и статус «жёлтый» на SCR-85 (FR-REM-05). `USE_EXACT_ALARM` не используется (NFR-STORE-03).
7. **Часовой пояс:** время хранится как локальное + зона; `zonedSchedule` с пакетом `timezone`. При смене пояса — пересчёт.
8. **Действия из уведомления** («Выполнено», «Отложить») обрабатываются фоновым обработчиком плагина. Он открывает базу, вызывает тот же сценарий и делает `reconcile`.

## 19. Сборка и CI

- **Репозиторий:** Git, основная ветка `main`, работа в ветках `feature/…`, слияние через pull request (даже для одного разработчика — для истории и CI).
- **GitHub Actions на каждый push и PR** (Linux, дешёвые минуты [Факт: TECH_RESEARCH §11]):
  1. `dart format --set-exit-if-changed`;
  2. `flutter analyze` (без предупреждений, NFR-MNT-04);
  3. проверка запрещённых импортов (§1.3);
  4. `dart test packages/core` с покрытием;
  5. `flutter test app`;
  6. тесты миграций;
  7. сборка Android debug APK (артефакт для эмулятора).
- **Codemagic** (500 бесплатных минут M2 в месяц [Факт]) — сборка iOS `--no-codesign` при слиянии в `main` и вручную. Артефакт `.ipa` ставится на iPhone через Sideloadly (D-003).
- **Окружения (flavors):** `dev` (отдельный bundle id `kz.uassistant.dev` [П], значок с пометкой, логи debug) и `prod`. Можно держать обе версии на одном телефоне.
- **Версионирование:** SemVer `1.0.0+номер_сборки`; номер сборки увеличивается в CI.
- **Зависимости:** фиксированные версии в `pubspec.lock` (в репозитории). Обновление — отдельным PR с прогоном всех тестов.
